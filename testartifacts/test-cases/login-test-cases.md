# Login — Test Cases

**Workflow:** Login  
**Generated:** 2026-08-30  
**Scope:** All authentication, role-access, session, and logout behaviours for the Student Management System login page (`/ui/login.html`).

---

## Implementation Notes (for test execution context)

- Authentication is **client-side only** — credentials are hardcoded in `static/login.html`; there is no API call on login.
- On success, four `sessionStorage` keys are set: `sms_auth=true`, `sms_user=<username>`, `sms_role=<role>`, `sms_label=<display label>`.
- Username input is **trimmed and lowercased** before comparison (e.g. `" ADMIN "` resolves to `admin`).
- On failure, the error banner is shown, the password field is cleared, and password input is focused.
- The main app (`app.js`) guards every page load: if `sms_auth !== 'true'`, the browser is redirected to `/ui/login.html`.
- Restricted pages render an **"Access Restricted"** div with the user's role name — no data is shown.
- There is **no server-side session, no account lockout, and no session expiry** in the current implementation.

---

## Assumptions

- **A_01 — No lockout threshold defined:** No account lockout after repeated failed attempts is implemented or documented. Test cases flag this as a risk but do not assert a lockout count.
- **A_02 — No session timeout:** Session persists until the browser tab/window is closed or logout is clicked. No idle timeout is implemented.
- **A_03 — No audit logging:** Credential attempts are not logged server-side; log-pollution tests are not applicable.

## Gaps & Risk Flags

| ID | Gap / Risk | Recommendation |
|---|---|---|
| GAP_01 | No server-side authentication — credentials are hardcoded in client-side JS | Any user who reads the page source can see all credentials. Raise to product owner if production deployment is planned. |
| GAP_02 | No account lockout after repeated failures (TC_LOGIN_N15) | Recommend adding a threshold (e.g. 5 attempts) with a timed lockout or CAPTCHA. |
| GAP_03 | No session expiry / idle timeout | A stolen session token (via sessionStorage access) remains valid indefinitely within the tab lifetime. |
| GAP_04 | `sms_role` in sessionStorage can be manually edited via DevTools to escalate privileges | Since role-based access enforcement is also client-side, a user who edits `sms_role=admin` gains admin UI access. Flag as architectural risk. |
| GAP_05 | Password masking: no "show/hide password" toggle documented | Confirm with UX whether this is in scope; currently not implemented. |
